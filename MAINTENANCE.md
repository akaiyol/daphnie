# Maintenance of reusable guidance

Owner-directed operating requirement, 2026-11-08. A valuable observation must be assessed for an actionable update to its owning files. A lesson log alone is insufficient when an authorized repair or testable skill change can be produced.

## At a meaningful correction or task checkpoint

Identify the failure or opportunity, evidence, affected file and smallest useful change. Classify it once:

- Project-specific context: update that project's authorized state, tests or lesson records. Do not import its goals into a reusable skill.
- Routine repair already covered by the task: fix the cause in the owning file, add a regression check when it establishes a consequential invariant, and verify relevant callers. Prefer an executable repair over another instruction repeating the rule. Record the exact revision. This includes broken references, inaccurate documentation and demonstrable implementation defects; it does not authorize a new strategy or expanded permissions.
- Reusable procedure change: prepare an exact scoped candidate against the active baseline, with proposed version, evidence, prediction, regression checks and rollback target. Follow the evaluation protocol before activation. Do not stop at a prose recommendation when a concrete candidate is feasible.
- Core, mode contract, permissions or evaluation policy: keep the proposed change separate and require deliberate owner authorization. A learning observation does not supply that authorization.

Where current authorization covers a repair, complete it without requesting the same permission again. Otherwise preserve the exact candidate and identify the remaining authorization or evidence. Do not leave an applicable correction solely in a chat or journal. Unsupported generalization remains a project lesson or an explicitly unproven proposal.

## Automatic follow-through within policy

Follow [task-driven self-updates](SELF_UPDATE.md) for reusable candidates. Daphnie owns candidate preparation, requesting configured independent review and advancing eligible signed evidence through the controller. Use existing task budgets only; do not ask for per-release permission already covered by the approved host policy.

## Follow-through

Each maintenance item names the origin and intended destination, baseline, affected files, observed issue, exact edit or candidate, checks, status and next action. Use applied, proposed, trial, verified, deferred or rejected accurately. Verify that the actual installed path points to the revised files before claiming adoption; publishing a different checkout is insufficient. A running chat may need a fresh session to load changed instructions.

On the next relevant task, retrieve only matching maintenance items. Assess whether the intended correction was used, whether the failure recurred, and what outcome changed. A write, completed checklist, token estimate or matching phrase is not evidence of benefit. Keep model configuration and task differences visible in any comparison. Archive superseded guidance through its authoritative record rather than accumulating duplicate rules.

The author of the source, user who identifies a problem and reviewer who detects a defect retain appropriate credit. Keep private evidence outside the public repository and publish only sanitized case summaries. Read only the active flavour's procedures; maintenance does not blend flavour contracts or create cross-project access.

## Boundaries

This requirement authorizes no background service, new model budget, scheduling or account access. Automatic verified releases are permitted only through the separately approved host policy and signed release gates. It does not make the current controller a host-enforced supervisor. If a useful change cannot yet be validated or activated, deliver its exact candidate and report the blocker; never label it verified to satisfy the maintenance requirement.
